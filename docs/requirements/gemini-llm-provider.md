## 0. 배경 / 목적

`CLAUDE.md`는 "LLM Provider는 추상화되어 있고(`LlmEvaluationProvider`), `gemini`는 추후 Google AI Studio 키 확보 시 연동하며, 세 프로바이더 모두 동일한 구조화 출력 스키마를 반환해야 한다"고 규정한다. 이제 키가 확보되었으므로, 지금까지 `mock` 프로바이더로만 검증해 온 채점 파이프라인(마스킹 → 평가시트 로딩 → LLM 채점 → 서버 재집계 → 게이팅 판정 → 저장 → 화면 표시)을 **실제 LLM 호출로 end-to-end 검증**한다.

목적은 두 가지다.

1. **실사용 가치**: 템플릿 기반 mock 점수/사유 대신 실제 LLM이 생성한 항목별 점수·사유·코칭을 QA 관리자에게 제공한다.
2. **추상화 검증(Phase 1 NFR-2.3의 실증)**: 집계/게이팅/저장/UI 코드를 한 줄도 바꾸지 않고 `LLM_PROVIDER=gemini`만으로 실 프로바이더가 붙는지 확인한다. 이 검증이 실패하면 추상화 설계 자체를 수정해야 한다.

### 0.1 현황 실측 결과 (PM 전제 정정)

| 항목                    | PM 프롬프트 전제                    | 실제 코드 확인 결과 (2026-09-12)                                                     |
| ----------------------- | ----------------------------------- | ------------------------------------------------------------------------------------ |
| Anthropic 프로바이더    | "이미 구현된 실제 프로바이더"       | **스텁이다.** `evaluate()`가 항상 `Error`를 throw하며 SDK 의존성도 없다               |
| `apps/api` 의존성       | Anthropic SDK 사용 중               | `package.json`에 LLM SDK가 **하나도 없다**(`@anthropic-ai/sdk`, `@google/genai` 모두 없음) |
| 재시도/타임아웃 패턴    | Anthropic 구현에 존재               | 코드에 없다. 주석으로 "SDK 기본 재시도에 맡긴다"는 **의도만** 기록되어 있다            |
| 프로바이더 오류 상태코드 | "타임아웃/네트워크 에러 → 502"      | 현재 `EvaluationService.invokeProvider`는 모든 프로바이더 throw를 **500**으로 매핑한다 |

**따라서 Gemini가 이 프로젝트의 첫 실 프로바이더이며, 이 기능에서 정하는 타임아웃/재시도/에러 매핑/스키마 전달 방식이 이후 Anthropic 구현이 따라야 하는 기준 패턴이 된다.** "Anthropic과 동일한 패턴을 따른다"는 요구사항은 "Anthropic 구현 시 재사용 가능한 형태로 패턴을 세운다"로 재해석하여 §FR-9에 반영한다.

## 1. 사용자 시나리오

### 1.1 QA 관리자 (주 사용자)

1. QA 관리자는 통신 도메인 상담 트랜스크립트를 결과 입력 화면에 붙여넣고 도메인을 선택해 제출한다.
2. 서버는 PII를 마스킹한 뒤 Gemini에 채점을 의뢰하고, 수 초~수십 초 후 결과 화면에 항목별 점수·사유, 카테고리 소계, 게이팅 결과, 총점/등급, AI 코칭이 표시된다.
3. 화면 하단 메타 영역에 `Provider: gemini (<모델명>)`이 표시되어, QA 관리자는 이 결과가 mock이 아닌 실제 LLM 판정임을 구분할 수 있다.
4. 채점 사유가 실제 대화 내용을 인용하므로, QA 관리자는 mock과 달리 사유의 타당성을 검토하고 필요 시 점수 수동 보정(FR-10, Phase 1)을 수행한다.

### 1.2 상담사 (간접 사용자)

- 상담사는 자신의 평가 결과(점수·사유·코칭)를 확인한다. 결과 신뢰성이 mock 템플릿보다 높아지는 대신, **같은 대화를 두 번 채점하면 점수가 미세하게 달라질 수 있다**(LLM 비결정론성). 이 차이가 평가 이의 제기로 이어질 수 있으므로, 게이팅 판정 같은 중대한 결과는 사람이 최종 확인한다는 운영 원칙을 전제로 한다(§7 D-5).

### 1.3 개발자 / 운영자

- 로컬 개발은 기본값 `LLM_PROVIDER=mock`으로 계속 수행한다(API 비용·쿼터 소모 없음, 결정론적 테스트 유지).
- 실 프로바이더 확인이 필요할 때만 `.env`에서 `LLM_PROVIDER=gemini`로 바꿔 재기동한다. 코드 변경은 없다.
- 키가 없거나 모델명이 잘못된 환경에서 `gemini`를 선택하면, 첫 요청이 500으로 실패하기 전에 **기동 시점에** 원인을 알 수 있어야 한다(§FR-8).

## 2. 기능 요구사항 (FR)

### FR-1. `GeminiLlmEvaluationProvider.evaluate()` 실호출 구현

- **FR-1.1** `apps/api/src/evaluation/llm/gemini-llm-evaluation.provider.ts`의 스텁을 Google Gemini API 실호출 구현으로 대체한다. `LlmEvaluationProvider` 인터페이스 시그니처(`evaluate(request): Promise<LlmEvaluationResponse>`)는 변경하지 않는다.
- **FR-1.2** 반환값은 `LlmEvaluationResponse` 계약을 그대로 충족한다: `items[]`(itemId/score/reason, 게이팅 항목은 passFail 포함), `coaching`(goodPoints 1~3, improvements 1~3), `profanityCheck`(detected, matches), `providerMeta`.
- **FR-1.3** `providerMeta.provider`는 고정 문자열 `"gemini"`(`LlmProviderId` 유니온에 이미 존재), `providerMeta.model`은 **실제 호출에 사용된 모델명**, `providerMeta.latencyMs`는 요청 직전~응답 파싱 직후까지의 실측 경과 시간(ms, 정수)이다. 재시도가 발생한 경우 총 경과 시간을 기록한다.
- **FR-1.4** `LlmEvaluationRequest.evalSheet`로 전달된 **단일 도메인 평가시트만** 프롬프트에 포함한다. 전체 10종을 전송하지 않는다.
- **FR-1.5** 프로바이더는 상태를 갖지 않으며(요청 간 대화 이력·캐시 공유 없음), 동시 요청에 대해 안전해야 한다.

### FR-2. 모델 및 실행 파라미터 설정 (env)

- **FR-2.1** 모델명은 env `GEMINI_MODEL`로 설정 가능해야 한다(`ANTHROPIC_MODEL`과 동일한 컨벤션). 코드에 모델명을 하드코딩하지 않고, 상수 기본값 + env 오버라이드 구조로 둔다.
- **FR-2.2** **기본 모델명은 이 문서에서 확정하지 않는다.** 요구사항 분석 시점에 최신 모델 목록을 검증할 수 없었으므로(웹 검색 도구 미사용 환경), 다음 절차로 `backend-implementer`가 확정하고 그 결과를 `.env.example`과 `docs/decisions/`에 기록한다 — §7 D-1.
  1. `GEMINI_API_KEY`로 모델 목록 조회 API(`GET {base}/v1beta/models`)를 호출해 **현재 키로 실제 사용 가능한** 모델명을 확인한다.
  2. 그중 **구조화 출력(JSON 모드 / response schema)을 지원**하고, 장문 입력(평가시트 + 트랜스크립트)을 처리할 수 있으며, 비용·쿼터가 합리적인 안정 버전(preview/experimental 아님)을 기본값으로 선정한다.
  3. 선정 근거(모델명, 구조화 출력 지원 확인 방법, 컨텍스트 한도)를 문서에 남긴다.
- **FR-2.3** 다음 실행 파라미터를 env로 노출하고 코드에 합리적 기본값을 둔다. 기본값은 채점 일관성(낮은 temperature)과 응답 완결성(충분한 출력 토큰) 우선이다.

| env                        | 용도                                    | 기본값(권고)                         | 비고                                                      |
| -------------------------- | --------------------------------------- | ------------------------------------ | --------------------------------------------------------- |
| `GEMINI_API_KEY`           | API 인증 키                             | (없음, 필수)                         | `.env`에만 존재. `.env.example`은 빈 플레이스홀더 유지    |
| `GEMINI_MODEL`             | 채점 모델명                             | **미확정 — D-1에서 확정**            | 추측 금지. 확정 전에는 값 미설정 시 기동 실패(FR-8)       |
| `GEMINI_TIMEOUT_MS`        | 단일 HTTP 호출 타임아웃                 | `60000`                              | 호출 1회 기준. 재시도마다 개별 적용                        |
| `GEMINI_MAX_RETRIES`       | 일시적 오류 재시도 횟수                 | `2`                                  | 프로바이더 내부 재시도(§FR-7)                              |
| `GEMINI_MAX_OUTPUT_TOKENS` | 응답 최대 출력 토큰                     | `8192` (D-1에서 모델 한도 확인 후 조정) | 항목 14개 × 사유 + 코칭을 담기에 충분해야 함               |
| `GEMINI_TEMPERATURE`       | 샘플링 온도                             | `0`                                  | 채점 편차 최소화. 0 미지원 모델이면 최소값으로 조정        |
| `GEMINI_API_BASE_URL`      | API 베이스 URL 오버라이드               | 공식 엔드포인트                      | **테스트 전용 목적 포함**(로컬 스텁 서버로 오류 재현, §AC-3/AC-5) |
| `GEMINI_THINKING_BUDGET`   | 사고(thinking) 토큰 예산 (모델이 지원할 때만) | 미설정(모델 기본)                | D-1에서 지원 여부 확인. 출력 토큰을 잠식할 수 있으므로 주의 |

- **FR-2.4** 숫자형 env가 비어 있거나 숫자로 파싱되지 않으면 기본값으로 대체하고 경고 로그를 남긴다(값 자체는 로그 가능 — 비밀이 아님).

### FR-3. 구조화 출력 스키마 전달 (배점 상한의 API 레벨 강제)

- **FR-3.1** `CLAUDE.md` 핵심 설계 원칙(요청마다 동적 스키마 생성 + 항목별 `score`에 `maximum: item.maxScore` 지정)을 Gemini에서도 유지한다. 자유 텍스트 응답을 파싱하는 방식은 허용하지 않는다. 구조화 출력(JSON 응답 모드 + 응답 스키마)을 사용한다.
- **FR-3.2** 스키마 생성 로직은 `schema-builder.ts`를 **재사용하거나 그 옆에 Gemini 방언 어댑터를 추가**한다. 평가시트 구조로부터 스키마를 유도하는 로직이 프로바이더별로 중복 구현되어서는 안 된다.
- **FR-3.3** Gemini의 응답 스키마 방언은 Anthropic tool `input_schema`와 다를 수 있다. 다음 문법 요소는 **지원 여부를 실호출로 검증**한 뒤 사용한다. 미지원 요소는 대체 표현으로 우회한다(§7 D-2).

| 현재 `buildEvaluationResponseJsonSchema`가 사용하는 요소 | 위험                                                        | 우회 방안                                                 |
| -------------------------------------------------------- | ----------------------------------------------------------- | --------------------------------------------------------- |
| `itemId: { const: ... }`                                 | `const` 미지원 가능성이 높다                                | `enum: [단일값]` 또는 itemId를 객체 key로 승격(아래 G-2)   |
| `items: { anyOf: [항목별 스키마 N개] }`                  | 배열 요소별 서로 다른 `maximum`을 표현하기 위한 구조         | itemId를 key로 하는 객체 스키마로 변경(G-2 권고)           |
| `additionalProperties: false`                            | 미지원 가능성                                               | 서버측 zod `.strict()`가 이미 방어하므로 생략 가능          |
| `minLength` / `minItems` / `maxItems` / `maximum`         | 지원 가능성 높음(검증 필요)                                  | 미지원 시 프롬프트 지시문 + 서버 검증으로 대체              |

- **FR-3.4 (권고 형태 G-2)** 항목 결과를 배열이 아니라 **itemId를 property key로 하는 객체**로 받는 스키마를 권고한다. 각 key의 `score`에 해당 항목의 `maximum: item.maxScore`를 직접 지정할 수 있어 `const`/`anyOf` 없이도 배점 상한을 API 레벨에서 강제할 수 있고, 항목 누락도 `required`로 강제된다. 프로바이더는 이 객체를 `items[]` 배열로 **형태 변환만** 수행한다(§FR-5.2).
- **FR-3.5** 프롬프트(system instruction)에도 항목별 배점 상한과 게이팅 항목 여부를 명시하여, 스키마 강제와 지시문이 이중으로 작동하게 한다.

### FR-4. 프롬프트 구성

- **FR-4.1** 프롬프트는 다음 요소로 구성한다: (a) 역할·과업 정의(콜센터 QA 평가자), (b) 평가시트 컨텍스트(도메인명, 주요 상담 유형, 카테고리/항목/세부평가내용/배점/게이팅 여부), (c) 게이팅 판정 규칙(`evalSheet.gatingPolicy` 문구 사용), (d) 마스킹된 트랜스크립트, (e) 출력 형식 규칙(한국어, 사유는 대화 근거 기반, 추측 금지).
- **FR-4.2** 마스킹 placeholder(`[전화번호]`, `[주민등록번호]` 등)가 원문 PII를 대체한 값임을 프롬프트에 설명하여, 모델이 이를 "상담사가 이상한 말을 했다"로 오판하거나 감점 근거로 삼지 않게 한다.
- **FR-4.3** 코칭(FR-9, Phase 1)은 goodPoints 1~3개 / improvements 1~3개, **상담사에게 직접 전달되는 존중하는 어조**의 한국어로 생성하도록 지시한다(mock의 어조와 일관).
- **FR-4.4** 프롬프트 텍스트는 코드 내 상수 또는 별도 템플릿 모듈로 분리해 리뷰 가능하게 둔다. 평가시트 직렬화는 JSON 그대로 삽입하거나 사람이 읽기 쉬운 표로 변환하되, **어느 쪽이든 `disclaimer`/`sourceCitation`을 포함할지 여부를 명시**한다(권고: 컴플라이언스 항목 근거로 `sourceCitation`은 포함, `disclaimer`는 제외 — 채점과 무관한 내부 면책 문구).
- **FR-4.5** 사유(`reason`)에 **원문 PII를 복원하려는 시도나 placeholder 해석 추측을 포함하지 말 것**을 명시적으로 지시한다.

### FR-5. 응답 파싱 — "최소 파싱" 원칙 (계약 불변)

- **FR-5.1** 프로바이더는 **검증·보정 책임을 지지 않는다.** 점수 clamp, 반올림, 누락 항목 채우기, 기본값 대체, 사유 문구 생성/치환을 프로바이더에서 수행해서는 안 된다. 이 책임은 `EvaluationService`(구조 위반 → 502 / 값 범위 위반 → 재시도 → clamp → `manual_review`)에 있으며, Gemini 응답이 스키마를 벗어나도 그 방어 로직이 그대로 작동해야 한다.
- **FR-5.2** 프로바이더가 허용되는 변환은 다음으로 한정한다.
  1. JSON 텍스트 → 객체 파싱(`JSON.parse`).
  2. FR-3.4 채택 시, itemId-key 객체 → `items[]` 배열로의 **형태 변환**(순서는 평가시트 항목 순서를 따른다).
  3. 게이팅이 아닌 항목에서 모델이 보낸 `passFail` 제거(선택). `score`/`reason`은 손대지 않는다.
  4. `providerMeta` 주입.
- **FR-5.3** 모델이 반환하지 않은 itemId는 **만들어내지 않는다**. 결과적으로 `items[]`에 누락이 생기면 `EvaluationService`가 502로 거부한다(의도된 동작).
- **FR-5.4** `score`가 문자열·소수 등으로 오면 **형 변환하지 않고 그대로 전달**한다(값 범위 위반 경로가 재시도 → `manual_review`로 처리). 단, 이 경우 재시도까지 실패하면 clamp 결과가 0점이 될 수 있음을 알려진 한계로 문서화한다.
- **FR-5.5** 응답에 계약 외 필드(예: `originalScore`, `overridden` 등 감사 추적 전용 필드)가 섞여 오면 제거하지 않고 그대로 전달한다 — zod `.strict()`가 502로 차단하는 것이 설계 의도다(Phase 1 리뷰 N-1).

### FR-6. `profanityCheck` 산출 출처

- **FR-6.1 (권고안 = 로컬 산출)** `profanityCheck`는 Gemini에게 요청하지 않고, mock 프로바이더와 동일하게 `@auto-qa/pii-mask`의 `detectProfanity(maskedTranscript)` 결과를 사용한다. 근거:
  - Phase 3에서 비속어 탐지는 **옵션 B(자체 규칙 기반, fail-open)** 로 확정되었고 골든 코퍼스 회귀 테스트(AC-P)로 오탐/미탐을 통제한다. LLM 판정으로 바꾸면 이 통제 수단과 결정론성이 무력화된다.
  - 비속어 배지는 **상담사 개인 평가에 직접 노출**되는 신호다(Phase 3 §1.1). 비결정론적 판정에 맡길 대상이 아니다.
  - 탐지된 문장을 LLM이 그대로 되돌려주는 경로를 만들지 않음으로써, 비속어 원문이 응답/저장에 남을 위험을 줄인다(Phase 1 FR-8.3).
- **FR-6.2** 채택 시 Gemini에 전달하는 응답 스키마에서 `profanityCheck`를 제외하고, 프로바이더가 로컬 결과를 주입해 `LlmEvaluationResponse`를 완성한다(외부 계약은 불변 — 세 프로바이더 응답 타입 동일).
- **FR-6.3** PM이 "LLM 판정" 방식을 택하는 경우(§7 D-3), Phase 3 AC-P 골든 코퍼스는 `gemini` 프로바이더에 적용되지 않음을 문서에 명시하고, `detected=true`인데 `matches`가 비는 케이스가 502를 유발함을 프롬프트/스키마로 방지해야 한다.

### FR-7. 오류 분류 · 재시도 · 타임아웃

- **FR-7.1** 모든 HTTP 호출에 `GEMINI_TIMEOUT_MS` 타임아웃을 적용한다(`AbortController` 또는 SDK 타임아웃 옵션). 타임아웃 없는 호출은 허용하지 않는다.
- **FR-7.2** 일시적 오류(429 rate limit, 500/502/503/504, 네트워크 단절·DNS·소켓 에러, 타임아웃)는 프로바이더 내부에서 최대 `GEMINI_MAX_RETRIES`회 재시도한다. 지수 백오프 + 지터를 적용하고, 서버가 `Retry-After`류 힌트를 주면 우선 존중한다.
- **FR-7.3** 영구적 오류(400 잘못된 요청/스키마 거부, 401·403 인증/권한, 404 모델 없음, 안전 필터로 인한 차단)는 재시도하지 않고 즉시 실패한다.
- **FR-7.4** 응답이 정상 종료되지 않은 경우(출력 토큰 한도 초과로 JSON이 잘림, 안전 필터 차단, 후보 없음 등)는 **깨진 JSON을 억지로 복구하지 않고** 명확한 에러로 실패시킨다. 에러 메시지에는 종료 사유 코드·모델명만 포함하고 응답 텍스트를 포함하지 않는다.
- **FR-7.5** 재시도 소진 후에는 프로바이더가 `Error`(또는 전용 에러 클래스)를 throw한다. `EvaluationService.invokeProvider`가 이를 잡아 **500 계열**로 매핑하고 트랜스크립트/평가 레코드를 저장하지 않는다(Phase 1 NFR-3.2 "LLM 호출 실패/타임아웃 → 500/504 계열", 원자적 처리).
- **FR-7.6** 상태코드 매핑 계약(현행 유지, 변경 금지):

| 상황                                                    | 프로바이더 동작            | API 응답        | 저장 여부      | 사용자 노출                       |
| ------------------------------------------------------- | -------------------------- | --------------- | -------------- | --------------------------------- |
| 네트워크 오류·타임아웃·429·5xx (재시도 소진)             | throw                      | **500**         | 저장 안 함     | 실패 안내 + 재시도 버튼           |
| 인증/권한/모델 없음/요청 거부                            | throw (재시도 없음)        | **500**         | 저장 안 함     | 동일(원인은 서버 로그에만)        |
| 응답 잘림·안전 차단·JSON 파싱 실패                       | throw                      | **500**         | 저장 안 함     | 동일                              |
| 항목 누락/중복/미지 itemId, coaching·profanity 형식 위반 | 응답 그대로 반환           | **502**         | 저장 안 함     | 실패 안내 + 재시도 버튼           |
| score 범위·정수 위반, reason 공백, 게이팅 passFail 누락  | 응답 그대로 반환           | 200             | `manual_review`로 저장 | 수동 검토 배지 표시       |

> PM 프롬프트의 "타임아웃/네트워크 에러 → 502"는 현행 구현(500) 및 Phase 1 NFR-3.2와 어긋난다. 이 문서는 **현행 500 유지**를 확정 요구사항으로 한다(§7 D-4 참조). 502는 "LLM이 응답했으나 계약을 위반한 경우" 전용 신호로 남긴다 — 두 실패를 구분하는 것이 진단에 유리하고, 기존 테스트 스윗(`evaluation.service.spec.ts`)과의 호환도 유지된다.
- **FR-7.7** `EvaluationService`가 값 범위 위반으로 `evaluate()`를 재호출할 수 있으므로(최대 1회), 최악의 경우 총 호출 시간은 `2 × (타임아웃 × (재시도+1))`이 된다. 이 상한을 계산해 문서화하고, 과도하면 기본값(타임아웃 60s / 재시도 2)을 조정한다.

### FR-8. 설정 누락 시 fail-fast

- **FR-8.1** `LLM_PROVIDER=gemini`인데 `GEMINI_API_KEY`가 비어 있으면, **애플리케이션 기동 시점에** 명확한 한국어 메시지로 실패한다(예: "LLM_PROVIDER=gemini이지만 GEMINI_API_KEY가 설정되지 않았습니다. .env를 확인하세요."). 키 값 자체는 메시지에 포함하지 않는다.
- **FR-8.2** `GEMINI_MODEL`이 비어 있고 코드 기본값도 확정되지 않은 상태라면 동일하게 기동 시 실패한다. D-1 확정 후에는 기본값으로 동작한다.
- **FR-8.3** `LLM_PROVIDER=mock`(기본값)일 때는 Gemini 관련 env가 전혀 없어도 정상 기동해야 한다. mock 개발 환경에 새로운 필수 설정을 추가하지 않는다.
- **FR-8.4** 기동 시 어떤 프로바이더가 선택되었는지 1줄 로그를 남긴다(예: `LLM provider: gemini (model=<모델명>)`). 키는 출력하지 않는다.

### FR-9. 재사용 가능한 공통 패턴 (Anthropic 구현 대비)

- **FR-9.1** 타임아웃·재시도·백오프·에러 분류 로직은 Gemini 전용 코드에 묻지 말고, **프로바이더 간 재사용 가능한 형태**(예: `llm/http-retry.ts` 같은 작은 헬퍼 또는 명확히 분리된 private 메서드)로 구현한다. 이후 Anthropic 구현이 동일 정책을 복붙 없이 따를 수 있어야 한다.
- **FR-9.2** 프로바이더 공통 규약을 코드 주석 또는 `llm/README.md`에 요약해 남긴다: "동적 스키마로 구조화 출력 요청 → 최소 파싱 → providerMeta 주입 → 검증/보정은 하지 않음 → 실패 시 throw".
- **FR-9.3** `evaluation.module.ts`의 프로바이더 선택 팩토리는 변경하지 않는다(이미 `gemini` 분기 존재).

### FR-10. 관측성 / 로깅

- **FR-10.1** 호출 1건당 다음을 구조적으로 로그한다: provider, 모델명, `domainId`, 시도 횟수, 총 latencyMs, 응답 종료 사유, 토큰 사용량(입력/출력/총계, 응답이 제공하는 경우).
- **FR-10.2** 로그·에러 메시지에 **트랜스크립트 원문, 마스킹된 텍스트 스니펫, 프롬프트 전문, 모델 응답 본문, API 키**를 절대 포함하지 않는다(Phase 1 NFR-1.2, 리뷰 M-5와 동일 원칙).
- **FR-10.3** 디버깅 목적의 프롬프트/응답 덤프 기능을 추가하는 경우, 기본 비활성 env 게이트(예: `GEMINI_DEBUG_DUMP=0`)를 두고 **마스킹된 텍스트만** 대상으로 하며, 문서에 "운영 환경 사용 금지"를 명시한다. 기본 권고는 이 기능을 **추가하지 않는 것**이다.

### FR-11. 문서 / 설정 파일 갱신

- **FR-11.1** `.env.example`의 Gemini 절을 갱신한다: `GEMINI_API_KEY=`(빈 값 유지), `GEMINI_MODEL=<D-1 확정값>`, 그리고 FR-2.3의 선택 env를 주석과 함께 추가한다. **실제 키 값은 어떤 파일에도 넣지 않는다.**
- **FR-11.2** `CLAUDE.md`의 LLM Provider 절에서 "gemini는 추후 연동" 문구를 현재 상태(연동 완료, 기본값은 여전히 mock)로 갱신한다.
- **FR-11.3** 모델 선정 근거와 Gemini 스키마 방언 우회 결정을 `docs/decisions/`에 ADR로 남긴다(D-1/D-2/D-3 결정 기록).

### FR-12. UI 영향

- **결론: UI 변경이 필요하지 않다. `ui-designer` 단계를 생략하고 `backend-implementer`로 직행할 수 있다.**

| 항목                        | UI 영향 | 근거                                                                                                       |
| --------------------------- | ------- | ---------------------------------------------------------------------------------------------------------- |
| Provider/모델 표시          | **없음** | `EvaluationMetaFooter`가 `Provider: {llmProvider} ({llmModel})`를 문자열로 그대로 렌더링한다(하드코딩 없음)   |
| 응답 스키마                 | **없음** | `EvaluationResultResponse`/`shared-types` 불변. `LlmProviderId`에 `'gemini'`가 이미 포함되어 있다             |
| 로딩/진행 상태              | **없음** | 로딩 상태는 Phase 1에서 이미 필수 구현됨. 실 LLM 지연(수 초~수십 초)도 기존 UI로 커버된다                    |
| 오류 화면                   | **없음** | 500/502 모두 기존 실패 안내 + 재시도 버튼 경로를 재사용한다                                                  |
| `manual_review` 배지        | **없음** | 기존 상태 표시 그대로 사용                                                                                  |

- **FR-12.1 (선택, 권고 아님)** 실 LLM 사용 시 응답이 느릴 수 있으므로 로딩 문구에 "AI가 채점 중입니다(최대 1분)" 수준의 안내를 추가하는 것은 `frontend-implementer` 재량으로 둔다. 별도 UI 스펙을 요구하지 않는다.

### 3.2 Gemini 요청 매핑 (개요)

| 요청 요소                 | 내용                                                                          |
| ------------------------- | ----------------------------------------------------------------------------- |


### 3.5 저장 스키마

- 변경 없음. `Evaluation.llmProvider="gemini"`, `Evaluation.llmModel=<모델명>`이 기존 컬럼에 저장된다. Prisma 마이그레이션 불필요.
- 프롬프트 전문, 모델 응답 원본(raw)은 저장하지 않는다(§4 NFR-1.4).

### 3.6 예외 케이스 취급

| 예외 케이스                                | 기대 동작                                                                        |
| ------------------------------------------ | -------------------------------------------------------------------------------- |
| 빈/10자 미만 트랜스크립트                  | Gemini 호출 전에 400(Phase 1 FR-1.2). 프로바이더까지 도달하지 않는다              |
| 존재하지 않는 `domainId`                   | 400(Phase 1 FR-11.4). 프로바이더 미호출                                          |
| 트랜스크립트가 해당 도메인과 무관한 내용   | 정상 채점 수행. 낮은 점수/게이팅 F가 나올 수 있으며 그것이 정상 결과다            |
| 대화가 극단적으로 짧음(10~30자)            | 정상 호출. 근거 부족 시 낮은 점수 + 사유에 근거 부족 명시를 프롬프트로 유도       |
| 트랜스크립트가 과도하게 긺(컨텍스트 초과)  | Gemini가 400 계열로 거부 → 재시도 없이 500. 입력 길이 상한 도입은 Out of scope(§6) |
| 모델이 한국어가 아닌 언어로 사유 작성      | 계약 위반은 아니므로 통과. 프롬프트로 억제하고 AC-1 수동 확인 항목에 포함          |
| 모델이 항목 하나를 빠뜨림                  | 502, 저장 안 함                                                                  |
| 모델이 배점을 초과한 점수 반환              | 스키마 `maximum`으로 1차 차단, 통과 시 재시도 → clamp → `manual_review`           |
| 안전 필터가 응답을 차단                    | 500. 비속어가 포함된 상담 대화에서 발생 가능 — AC-5에서 알려진 한계로 기록         |
| 무료 티어 쿼터 초과(429 지속)              | 재시도 소진 후 500. 로그에 429와 재시도 횟수가 남아 원인 파악 가능                 |

## 4. 비기능 요구사항 (NFR)

**NFR-1. PII / 보안**

- NFR-1.1 Gemini로 전송되는 텍스트는 `maskPii()`를 통과한 `maskedText`뿐이다. 프로바이더는 원문(`rawText`)에 접근할 수 없다(인터페이스상 도달 불가 — 이 성질을 테스트로 고정한다).
- NFR-1.2 `GEMINI_API_KEY`는 `.env`에서만 읽는다. 키를 로그·에러 메시지·예외 스택·HTTP 요청 URL 쿼리스트링·커밋·문서에 남기지 않는다. 키의 앞/뒤 일부만 출력하는 것도 금지한다.
- NFR-1.3 외부 전송이 발생하는 첫 기능이므로, "마스킹된 상담 텍스트가 Google 서버로 전송된다"는 사실을 `docs/decisions/` ADR에 명시한다. 사내 데이터 처리 정책상 외부 LLM 전송이 허용되는지는 PM/사용자 확인 사항이다(§7 D-6).
- NFR-1.4 프롬프트/응답 원본을 디스크·DB에 영속화하지 않는다(FR-10.3의 옵트인 디버그 덤프 제외, 기본 비활성).

**NFR-2. Provider 추상화 (Phase 1 NFR-2 유지)**

- NFR-2.1 `LLM_PROVIDER` 값 변경만으로 전환된다. 컨트롤러·집계·저장·UI 코드는 수정되지 않는다.
- NFR-2.2 `LlmEvaluationRequest/Response` 타입과 `schema-builder.ts`의 zod 계약은 이 기능에서 변경하지 않는다. 변경이 불가피하면 세 프로바이더 모두에 대한 영향 분석과 함께 별도 결정으로 기록한다.
- NFR-2.3 mock 프로바이더의 동작·테스트는 이 기능으로 인해 달라지지 않는다.

**NFR-3. 에러 처리**

- NFR-3.1 프로바이더 실패 시 부분 저장이 발생하지 않는다(현행 트랜잭션 구조 유지 — LLM 호출이 저장보다 앞선다).
- NFR-3.2 프로바이더가 던지는 에러 메시지는 사용자에게 그대로 노출되지 않으며(서비스가 일반화된 문구로 대체), 진단 정보는 서버 로그에만 남는다.
- NFR-3.3 재시도는 idempotent한 읽기성 호출에 한정되며, 재시도로 인해 중복 저장이 발생하지 않는다.

**NFR-4. 성능 / 비용**

- NFR-4.1 실 LLM 채점의 P50 응답 시간 목표는 **30초 이내**, 타임아웃 상한은 `GEMINI_TIMEOUT_MS`(기본 60초)로 둔다. 목표 미달 시 모델 선택(D-1) 또는 출력 토큰 설정을 재검토한다.
- NFR-4.2 평가시트 전체를 매 요청 전송하므로 입력 토큰이 크다. 실측 토큰 사용량을 로그로 남겨(FR-10.1) 1건당 대략 비용을 산출하고 배포 문서에 기록한다.
- NFR-4.3 기본 개발 환경은 계속 `mock`이어야 한다(CI/테스트가 실 API를 호출해 쿼터·비용을 소모하지 않게 한다 — §AC-10).

**NFR-5. 결정론성 — 비적용 명시**

- NFR-5.1 **Phase 1 AC-8(결정론적 Mock 재현성)과 Phase 3 AC-R-3의 "2회 제출 시 완전 동일" 조건은 `LLM_PROVIDER=gemini`에 적용되지 않는다.** 실제 LLM 호출은 temperature 0에서도 동일 출력을 보장하지 않는다.
- NFR-5.2 `gemini`에 대해 검증하는 것은 "동일한 값"이 아니라 **"계약 준수와 합리적 안정성"**이다: 스키마 준수, 배점 상한 준수, 항목 완전성, 그리고 동일 입력 2회 채점의 총점 차이가 과도하지 않을 것(관찰값을 테스트 리포트에 기록, 하드 임계값은 이번 범위에서 규정하지 않음).
- NFR-5.3 결정론이 필요한 회귀 테스트(스냅샷 등)는 계속 mock 또는 스텁 트랜스포트로 수행한다. 실 API를 CI 필수 경로에 넣지 않는다.

**NFR-6. 테스트 가능성**

- NFR-6.1 `GEMINI_API_BASE_URL`(FR-2.3) 또는 주입 가능한 트랜스포트/HTTP 클라이언트를 통해 **실제 네트워크 없이** 다음을 재현할 수 있어야 한다: 정상 응답, 구조 위반 응답, 값 범위 위반 응답, 타임아웃, 429, 5xx, 잘린 JSON, 안전 차단.
- NFR-6.2 실 API를 호출하는 테스트는 별도 태그/스크립트로 분리하고, 키가 없으면 자동 skip되도록 한다(기본 `pnpm test`를 깨지 않는다).

## 5. 수용기준 (AC)

### AC-1. 실 API end-to-end 채점 성공 (필수, 수동 1회 + 리포트 기록)

- Given `.env`에 유효한 `GEMINI_API_KEY`와 확정된 `GEMINI_MODEL`, `LLM_PROVIDER=gemini`가 설정되어 API가 기동된 상태에서
- When QA 관리자가 통신(`telecom`) 도메인 샘플 트랜스크립트를 제출하면
- Then 200 응답과 함께 결과 화면에 카테고리 소계 5건, 해당 평가시트의 **모든 항목**에 대한 점수·사유, 게이팅 결과, 총점/등급, 코칭(goodPoints 1~3 / improvements 1~3)이 표시된다.
- And `status === "completed"`이고, 저장된 `llmProvider === "gemini"`, `llmModel === <설정한 모델명>`, `latencyMs > 0`이다.
- And 사유는 한국어이며 해당 대화 내용에 근거한 서술이다(mock 템플릿 문구가 아님을 육안 확인).
- And 최소 1개 도메인(telecom)에서 성공하면 이 AC는 충족된다. 나머지 9종은 샘플 1건씩 스모크 실행을 권고(필수 아님).

### AC-2. 배점 상한 · 항목 완전성 준수

- Given AC-1의 실호출 결과에서
- Then 모든 항목이 `0 <= score <= item.maxScore`인 정수이고, itemId는 평가시트와 정확히 1:1 대응(누락·중복·미지 없음)한다.
- And 모든 게이팅 항목에 `passFail ∈ {"P","F"}`가 존재한다.
- And 게이팅 항목이 1건이라도 `F`이면 총점과 무관하게 `gatingResult === "탈락(재검토 필요)"`로 집계된다.

### AC-3. 구조 위반 응답 → 502, 저장 없음 (스텁 트랜스포트)

- Given 스텁 응답으로 (a) 항목 1건 누락, (b) 미지 itemId 포함, (c) `coaching.goodPoints`가 빈 배열, (d) 계약 외 필드(`overridden`) 포함 중 하나를 반환하도록 구성했을 때
- When 채점을 요청하면
- Then API는 **502**를 반환하고, `Transcript`/`Evaluation` 레코드가 생성되지 않는다.
- And 이 경로에서 Gemini 프로바이더는 응답을 보정하거나 항목을 채워넣지 않았다(FR-5.1 준수 확인).

### AC-4. 값 범위 위반 → 재시도 1회 → `manual_review`

- Given 스텁 응답이 1차·2차 모두 배점 초과 점수(또는 게이팅 항목 `passFail` 누락)를 반환하도록 구성했을 때
- When 채점을 요청하면
- Then 프로바이더 `evaluate()`가 정확히 2회 호출되고, 점수는 안전 범위로 clamp되며 `status === "manual_review"`로 저장되어 화면에 수동 검토 표시가 나타난다.
- And 1차 응답이 위반이고 2차가 정상이면 `status === "completed"`로 저장된다.

### AC-5. 타임아웃 / 네트워크 / 429 / 5xx → 500, 저장 없음

- Given 스텁 서버가 (a) 응답하지 않음(타임아웃), (b) 연결 거부, (c) 429 반복, (d) 503 반복, (e) 잘린 JSON, (f) 안전 필터 차단 형태의 응답을 반환할 때
- When 채점을 요청하면
- Then 각 케이스에서 API는 **500 계열**을 반환하고 레코드는 저장되지 않으며, 프론트는 실패 안내와 재시도 버튼을 표시한다.
- And (c)/(d)는 `GEMINI_MAX_RETRIES`만큼 재시도한 뒤 실패하고, (e)/(f)는 재시도 없이 즉시 실패한다.
- And 타임아웃 케이스에서 요청이 `GEMINI_TIMEOUT_MS` 경과 후 확실히 중단된다(행 걸림 없음).

### AC-6. 설정 누락 fail-fast

- Given `LLM_PROVIDER=gemini`이고 `GEMINI_API_KEY`(또는 `GEMINI_MODEL`)가 비어 있을 때
- When API를 기동하면
- Then 기동이 명확한 한국어 메시지와 함께 실패하고, 메시지에 키 값이 포함되지 않는다.
- And `LLM_PROVIDER=mock`(기본값)일 때는 Gemini env가 전혀 없어도 정상 기동하고 기존 mock 흐름이 동작한다.

### AC-7. 비밀키 비노출

- Given AC-1/AC-5의 모든 실행에서 수집된 서버 로그 전량과 API 오류 응답 본문에 대해
- When `GEMINI_API_KEY` 값(및 그 부분 문자열)을 검색하면
- Then 단 한 건도 발견되지 않는다.
- And 요청 URL이 로그에 남는 경우에도 키가 쿼리스트링으로 포함되어 있지 않다.
- And `git diff`/커밋 내용, `.env.example`, 문서에 실제 키 값이 존재하지 않는다.

### AC-8. PII 전송 경로 재확인

- Given 전화번호·주민등록번호·이메일·카드번호를 포함한 트랜스크립트를 제출했을 때
- When Gemini로 전송되는 요청 payload를 캡처하면(스텁 트랜스포트)
- Then payload 전체에 원문 PII 문자열이 **0건** 존재하고, 대신 `[전화번호]`/`[주민등록번호]`/`[이메일]`/`[카드번호]` placeholder만 존재한다.
- And 저장된 `maskedText`와 전송된 트랜스크립트가 동일하다(프로바이더가 텍스트를 가공하지 않음).
- And 모델 응답의 `reason`에도 원문 PII가 없다(실호출 결과 육안 + 정규식 확인).

### AC-9. 결정론성 비적용 확인

- Given `LLM_PROVIDER=gemini`로 동일 트랜스크립트를 2회 제출했을 때
- Then 결과가 완전히 동일하지 않아도 **실패로 간주하지 않는다**(Phase 1 AC-8 / Phase 3 AC-R-3은 mock 전용).
- And 두 결과 모두 AC-2(배점 상한·항목 완전성)를 충족하며, 총점 차이를 테스트 리포트에 관찰값으로 기록한다.
- And 결정론 기반 기존 회귀 테스트는 mock/스텁으로 수행되어 계속 통과한다.

### AC-10. Provider 전환 무코드 변경 (Phase 1 AC-10 재확인)

- Given 이 기능 구현 후
- When `LLM_PROVIDER`를 `mock` → `gemini` → `mock`으로 바꿔 각각 기동하면
- Then 애플리케이션 코드 변경 없이 모두 정상 동작하고, 기존 `apps/api` 테스트 스윗 전체가 통과한다.
- And 기본 `pnpm test`는 실 Gemini API를 호출하지 않는다(키 없이도 통과).

### AC-11. `profanityCheck` 계약 유지

- Given 비속어가 포함된 트랜스크립트를 `LLM_PROVIDER=gemini`로 제출했을 때
- Then `profanityDetected`/`profanityMatches`가 Phase 3 규칙(옵션 B)과 동일하게 산출되고, `matches[].maskedText`에 비속어 원문이 남지 않는다.
- And `detected === true`이면 `matches`가 1건 이상이다(502 유발 조건 미발생).
- And Phase 3 골든 코퍼스 테스트가 이 기능으로 인해 깨지지 않는다.

### AC-12. 관측성

- Given 실호출 1건이 성공했을 때
- Then 서버 로그에 provider, 모델명, domainId, 시도 횟수, latencyMs, 종료 사유, 토큰 사용량이 남는다.
- And 동일 로그에 트랜스크립트 텍스트·프롬프트 전문·응답 본문이 포함되지 않는다.

### AC-13. 문서 / 설정 갱신

- Then `.env.example`에 `GEMINI_MODEL` 및 선택 env가 주석과 함께 존재하고 `GEMINI_API_KEY`는 빈 값이다.
- And `CLAUDE.md`의 Gemini 관련 문구가 현재 상태로 갱신되었다.
- And `docs/decisions/`에 모델 선정(D-1), 스키마 방언 우회(D-2), SDK/전송 방식(D-3) 결정이 기록되었다.

## 6. Out of scope

이번 기능에서 **하지 않는다**(필요 시 별도 요구로 다룬다).

1. **Anthropic 프로바이더 실구현** — 이 기능이 세운 패턴을 따라 별도 작업으로 진행한다.
2. **도메인 분류(classification)의 LLM 연동** — 현재 도메인은 사용자가 선택하며, 자동 분류 모듈은 존재하지 않는다. `GEMINI_CLASSIFIER_MODEL` 도입도 이번 범위 밖이다.
3. **프로바이더 폴백/다중 호출** — Gemini 실패 시 mock/Anthropic으로 자동 전환, 2개 모델 교차 채점·앙상블, A/B 비교.
4. **스트리밍 응답 / 진행률 표시** — 항목별 점수를 스트리밍으로 흘려 보여주는 UI.
5. **프롬프트 캐싱, 배치 API, 컨텍스트 압축** 등 비용 최적화.
6. **채점 품질 벤치마크(LLM-eval 회귀)** — 정답 라벨 대비 정확도 측정, 프롬프트 튜닝 반복. Phase 5(테스트 자동화 확장) 과제로 이관한다.
7. **입력 길이 상한/청킹** — 컨텍스트 초과 트랜스크립트 분할 채점.
8. **비용 대시보드 / 쿼터 모니터링 / 요청 레이트 리미터**.
9. **UI 변경** — §FR-12 결론에 따라 없음(로딩 문구 미세 조정은 재량).
10. **오디오/파일 업로드, 멀티모달 입력, 실시간 상담 채점**.
11. **`profanityCheck`를 LLM 판정으로 전환** — D-3에서 권고안(로컬 산출)이 채택되는 한 범위 밖.
12. **모델 파인튜닝 / Vertex AI 전환** — Google AI Studio API 키 기반 호출만 다룬다.
