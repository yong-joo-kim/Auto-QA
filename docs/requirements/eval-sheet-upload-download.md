# 평가시트 Excel 업로드/다운로드 및 사용자 수정 기준 적용

## 개요

- 원본 양식(`3. 도메인별_상담사_평가시트_10종.xlsx`)과 동일한 구조로 평가시트 10종을 다운로드한다.
- 사용자가 평가항목/배점/게이팅/세부 기준을 수정해 업로드하면 이후 채점부터 수정된 기준으로 Auto QA가 동작한다.

## API

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/eval-sheets` | 도메인별 현재 평가시트 요약(버전, 항목 수, 수정 여부) |
| GET | `/eval-sheets/download` | 현재 유효 평가시트 10종을 xlsx로 다운로드 |
| POST | `/eval-sheets/upload` | multipart `file`(.xlsx, 최대 5MB). 전체 검증 후 반영(all-or-nothing) |
| DELETE | `/eval-sheets/:domainId/override` | 수정본 삭제, 기본(seed) 시트로 복원 |

## 동작 규칙

- 탭 이름 앞 번호(`1_`~`10_`)로 도메인을 식별한다. `00_안내` 등 번호 없는 탭은 무시한다.
- 읽는 열: 구분 / 평가항목 / 세부 평가내용 / 배점 / 게이팅(P/F 또는 -). 획득점수·비고·상담사 정보는 무시한다.
- 검증: 배점은 1 이상 정수, 게이팅은 `P/F` 또는 `-`, 항목명 중복 금지(구분이 달라도 같은 도메인 시트 안에서는 고유), 도메인별 배점 합계 100점.
- 카테고리/항목 ID: 같은 구분명·항목명이면 기존 ID를 유지하고, 신규는 자동 채번한다. 카테고리 배점은 항목 합계로 계산한다.
- 반영 시 버전은 `<major>.<minor>.<patch+1>`(예: 1.0.1)로 올라가며, patch는 복원(삭제) 이력과 무관하게 단조 증가한다. 내용 변경이 없는 탭은 반영하지 않는다.
- 길이 상한: 구분/평가항목명 100자, 세부 평가내용 1,000자, 주요 상담 유형/출처 문구 500자. 도메인당 항목 최대 100개, 시트(탭) 최대 20개. 같은 상한을 zod 스키마에도 적용한다.
- 업로드 파일 보호: 5MB 제한과 별도로 zip 압축 해제 크기 합계 50MB, 압축 항목 200개를 넘으면 로드 전에 거부한다. 행은 헤더 아래 300행까지만 읽는다.
- 수정본은 `data/eval-sheets-override/<domainId>.json`에 저장되며(env `EVAL_SHEETS_OVERRIDE_DIR`로 변경 가능, git 추적 제외) seed보다 우선한다.
- 카테고리/항목 ID는 한 번 발급되면 재사용하지 않는다. 도메인별 개정 이력(`data/eval-sheets-override/<domainId>.history.json`)에 발급된 ID와 최대 patch를 남기며, 기본값 복원 후에도 유지한다.
- 이미 저장된 채점 결과는 저장 당시의 항목/버전을 유지한다. 채점 시점의 평가시트 전체를 `Evaluation.evalSheetSnapshot`에 저장하고, 점수 보정 재계산과 결과 조회(출처/면책/도메인명 포함)는 이 스냅샷 기준으로 한다. 스냅샷 도입 이전 레코드(null)는 현재 시트의 버전이 저장된 버전과 같으면 현재 시트를, 다르면 저장된 항목/카테고리 점수 구조를 기준으로 재계산한다.
- 손상된 수정본 파일: `GET /eval-sheets`는 해당 도메인을 `corrupted: true`(기본 시트 기준 값)로 표시하고 복원/재업로드로 복구할 수 있다. 채점 요청은 503과 원인 메시지를, 다운로드는 500과 원인 메시지를 반환한다(조용히 기본 시트로 대체하지 않는다). 과거 결과 조회는 스냅샷 기준으로 계속 동작한다.
- 저장은 도메인 간 원자적이다(임시 파일 선기록 후 rename, 실패 시 롤백). 업로드/복원은 프로세스 내에서 직렬화된다.

## 운영 참고

- Docker 배포 시 `data/eval-sheets-override` 경로를 볼륨으로 마운트해야 컨테이너 재시작 후에도 수정본이 유지된다.
- 인증/권한 체크는 프로젝트 전반에 아직 없으므로 평가시트 변경 API도 동일하게 무인증이다. 사내망 외 노출 전 접근 제어가 필요하다.
- 단일 API 인스턴스를 전제로 한다. 여러 인스턴스가 같은 override 디렉터리를 공유하면 직렬화(프로세스 내 뮤텍스)가 보장되지 않는다.
- 접근 제어(인증 도입은 범위 밖, 임시 완화책): env `CORS_ORIGINS`(쉼표 구분, 미설정 시 `http://localhost:5173`, `http://127.0.0.1:5173`)에 없는 출처의 브라우저 요청은 CORS에서 거부하고, 업로드/복원 엔드포인트는 Origin 헤더가 허용 목록(또는 동일 호스트)이 아니면 403으로 거부한다. 배포 시 실제 웹 주소를 반드시 지정한다. `*`는 전체 허용이므로 운영에서 쓰지 않는다.
- 위 완화책은 브라우저 경유 CSRF만 막는다. Origin 헤더가 없는 직접 호출(curl 등)은 막지 못하므로, 사내망 외 노출 전에 인증/관리자 권한과 업로드 요청 제한(rate limit)을 도입해야 한다(추적 필요).
- `EVAL_SHEETS_DIR`를 리포지토리 밖으로 지정하면 `EVAL_SHEETS_OVERRIDE_DIR`도 쓰기 가능한 경로로 함께 지정한다(`.env.example` 참조).
