## 3. 발견 사항

### H-1 (High, 차단) 부분 구분자 16자리 카드번호가 Phase 1에선 마스킹, Phase 3에선 평문

- 위치: `packages/pii-mask/src/mask.ts:59`(`MANDATORY_SEP`), `:98-112`(카드 규칙 2종), `:185-203`(`classifyDigitRun` — `len === 16`만 카드 후보)
- 원인: Phase 1은 `\d{4}[-\s]?\d{4}[-\s]?\d{4}[-\s]?\d{4}`로 구분자가 **선택**이었다. Phase 3은 1단계에서 구분자를 3자리 **모두 필수**로 바꾸고 2단계는 "구분자 없는 순수 숫자열"만 분류하므로, 구분자가 **일부만** 있는 16자리 카드번호는 두 경로 모두에서 탈락한다.
- 실측:

| 입력 | Phase 1 | Phase 3 |
| ---- | ------- | ------- |
| `카드번호 4012-8888-88888886 입니다` | `[카드번호]` | 평문 잔존 |
| `카드번호 4012-88888888-8886 입니다` | `[카드번호]` | 평문 잔존 |
| `카드번호 40128888 8888 8886 입니다` | `[카드번호]` | 평문 잔존 |
| `카드 1234-56789012-3456` | `[카드번호]` | 평문 잔존 |
| `카드 1234-5678 9012-3456` (전 자리 구분자) | `[카드번호]` | `[카드번호]` |

- 영향: 실제 카드번호가 마스킹 없이 `maskedText`로 DB 영구 저장 + LLM 전송. 원문 미저장 정책상 사후 재마스킹 불가.
- FR-2.2 예외 아님: FR-2.2가 허용한 축소는 "**구분자 없는** 16자리에 Luhn 요구"뿐이고(`1234567890123456` Luhn 탈락 미마스킹은 정상), 위 케이스는 구분자가 있으므로 "구분자 있으면 Luhn 무관 마스킹" 대상이다. 구현이 "구분자 있음"을 "4-4-4-4 전 자리 구분자"로 과도하게 좁게 해석했다.
- 권고: ① 2단계 토큰 추출을 `\d+` → "숫자 + 내부 구분자"를 한 토큰으로(예: `\d(?:\d|[-. ](?=\d))*\d`) 확장해 총 자릿수로 분류(FR-1.5 권고 구조와 일치), 또는 ② 1단계에 "총 16자리 + 구분자 1개 이상(위치 무관)" 규칙 추가. 3케이스를 `PHASE1_REGRESSION_CASES`에 추가.

### M-1 (Medium) 계좌 규칙 변경으로 이메일 정규식의 2차 백트래킹이 노출 → NFR-3.2 위반

- 위치: `mask.ts:113-116`(이메일, 정규식 자체는 Phase 1과 동일), `:138-146`(FR-2.1 임계 도입), 적용 순서 `:234-240`(이메일이 계좌 규칙보다 먼저)
- 실측(규칙별 개별 계측으로 이메일 규칙에 귀속 확정):

| 입력 | Phase 1 | Phase 3 |
| ---- | ------- | ------- |
| `"12" + "-12"×4000` (12KB) | 1ms | 71ms |
| `"12" + "-12"×8000` (24KB) | 1ms | 258ms |
| `"12" + "-12"×34000` (102KB) | 1ms | **4,811ms** (NFR-3.2 9.6배 초과) |
| 정상 상담 트랜스크립트 100KB | 1ms | 20ms (mask 3ms + profanity 17ms) |

- 원인: `[A-Za-z0-9._%+-]+`가 `-`/`.`를 포함해 `12-12-12…` 전체를 삼킨 뒤 `@` 부재로 실패하고, `-`가 만드는 `\b` 위치마다 재시도 → O(n²). Phase 1에선 계좌 규칙이 이메일보다 **먼저** 해당 숫자열을 placeholder로 소비해 드러나지 않았다. Phase 3은 (정당하게) FR-2.1 임계를 도입해 짧은 숫자 그룹을 더 이상 치환하지 않으므로 긴 후보가 이메일 규칙까지 도달한다. **정규식은 그대로여도 Phase 3 변경으로 성능이 회귀**한 사례.
- 지수 폭발은 아니나 이벤트 루프를 5초 점유. `CreateTranscriptDto.rawText`에 `@MaxLength`가 없어 입력 상한도 본문 파서 기본값에만 의존.
- 권고: 수량자 상한 부여 — `[A-Za-z0-9._%+-]{1,64}@[A-Za-z0-9.-]{1,255}\.[A-Za-z]{2,}`. 실측 **4,739ms → 15ms**, 정상 이메일 탐지 유지 확인. 부수적으로 `rawText` 최대 길이 검증 권고(별건).

### M-2 (Medium) 계좌(구분자) 규칙에 공백 구분자를 추가해 요구사항에 없는 신규 과탐

- 위치: `mask.ts:61`(`RRN_ACCOUNT_SEP = '[-\s]'`), `:121-124`
- FR-1.1은 계좌에 **점** 금지만 규정했고 FR-1.4는 **무구분** 계좌에 문맥 키워드 필수를 요구했을 뿐, 공백 구분자 확장은 요구하지 않았다. 결과적으로 문맥 키워드 없이 "공백 3그룹 합계 10자리 이상"이 계좌로 치환된다(Phase 1은 전부 원문 보존):

| 입력 | Phase 3 결과 |
| ---- | ------------ |
| `요금은 15000 20000 25000 중 선택하세요` | `요금은 [계좌번호] 중 선택하세요` |
| `포인트 1000 2000 30000 적립되었습니다` | `포인트 [계좌번호] 적립되었습니다` |
| `견적 100000 200000 300000 원` | `견적 [계좌번호] 원` |
| `번호 1234 5678 9012` | `번호 [계좌번호]` |
| 숫자만 있는 4줄 (`1234` / `5678` / `9012` / `3456`) | `[카드번호]` (공백 클래스에 개행 포함) |

- 영향: 유출 방향은 아니나 금액·포인트 나열은 통신/카드 상담 빈출이며, 마스킹되면 "금액을 정확히 안내했는가" 항목의 채점 근거가 사라진다. 과탐을 줄이러 들어간 Phase에서 새 과탐 표면을 만든 셈(AC-R-2 취지 위반).
- 권고: 계좌 규칙 구분자를 하이픈으로 환원하거나, 공백 유지 시 문맥 키워드 근접을 필수화. 4케이스 코퍼스 추가.

### M-3 (Medium) 문맥 키워드 + 8자리 완화가 `YYYYMMDD` 날짜를 계좌로 오탐

- 위치: `mask.ts:188-192`(`hasAccountContext(...) && len >= 8`)
- 실측: `입금은 20260911 에 했습니다` → `입금은 [계좌번호] 에 했습니다`, `이체일 20260911 확인` → `[계좌번호]`, `송금 20241231 완료` → `[계좌번호]`
- 원인: `입금`/`이체`/`송금`은 날짜와 동일 문장에 등장할 확률이 가장 높은 키워드다. 1단계 하이픈 규칙에는 `(?!(?:19|20)\d{2}-\d{2}-\d{2})` 날짜 방어가 있는데(M-4 대응) 2단계 무구분 경로에는 동등 방어가 없다.
- 권고: `classifyDigitRun`의 8자리 후보에서 `(19|20)\d{2}` + 유효 월/일 형태를 제외. 3케이스 코퍼스 추가.

### M-4 (Medium) 비속어 미탐 표면 확대 + FR-3.1 "문장부호 기준 어절 분할" 미구현

- 위치: `profanity.ts:156`(`text.split(/(\s+)/)` — 공백만), `:136`(`ALLOWED_ENDINGS` 정확 일치), `profanity-data.ts:12-21`, `:59-63`
- FR-3.1은 "공백·**문장부호** 기준으로 어절 분할"을 규정하나 구현은 공백만 분할 + 어절 **양 끝** 부호만 제거하므로, 어절 내부 부호가 있으면 잔여 판정에서 탈락한다.
- Phase 1 → Phase 3 미탐 전환 11종(실측):

| 입력 | P1 | P3 | 성격 |
| ---- | -- | -- | ---- |
| `고객: 아니 씨발,진짜` | true | false | FR-3.1 문장부호 분할 미구현 |
| `고객: 씨발...진짜` | true | false | 동일 |
| `고객: 씨발새끼` | true | false | 복합어 사전 미등록(명백한 욕설) |
| `고객: 지랄하네` / `닥쳐라` / `씨발같은 소리` / `병신같이` / `지랄이야` / `개소리하지마` | true | false | 허용 어미 미포함 |
| `고객: 이 새끼가` / `새끼야` | true | false | `새끼` 어간 미등록 |
| `상담사: 저리 꺼져!` | true | false | FR-3.4 폴백 — 의도된 결정, 문서화 완료 |

- 평가: 방향은 §1.1이 허용하는 fail-open이고 AC-P-2 열거 케이스는 전부 통과 → **차단 아님**. 다만 (a) `씨발,진짜`류는 요구사항 문구 미준수에서 비롯됐고, (b) `씨발새끼`는 오탐 위험 없이 사전 한 줄로 회복 가능하다. 문장부호 분할을 도입해도 AC-P-1의 `병신년(丙申年)`은 `년` 잔여로 여전히 미탐(프로브 확인)이라 오탐 회귀 위험은 낮다.

## 4. 요구사항 §7 AC-L-3 "구현 편차 기록"(2026-09-12) 타당성

**타당하다(승인 권고).** 실측으로 전제를 확인: `1101234567890`은 월=`01`·일=`01`·성별코드=`1`로 FR-1.2 형태 조건을 우연히 전부 만족하므로, 원 예시(`주문번호 1101234567890` → 원문 보존)는 FR-1.2와 정면 모순이다. 구현은 `주문번호 1101234567890 입니다` → `주문번호 [주민등록번호] 입니다`, `계좌번호 1101234567890 입니다` → `계좌번호 [계좌번호] 입니다`로 동작하며, 전자는 §1.1 fail-closed에 부합한다(원 예시대로 보존했다면 주민번호 형태 문자열을 평문 저장하는 유출 경로가 된다). 대체값 `1199990000000`(월=99 무효)은 원 검증 의도를 유지하며 실측 원문 보존 확인. 기록 위치(요구사항 §7 각주 + `mask-corpus.ts:85-97`)와 근거 서술도 FR-6.2 충족.

## 6. NFR-1 (PII/보안) 점검

- 순수성(NFR-1.2): 4개 모듈 전부 파일 I/O·네트워크·`Date`·`Math.random` 없음, 런타임 의존성 0(AC-N-3).
- 원문 유출 경로(NFR-1.3): 두 모듈에 logger/`console`/`throw` 없음. 반환값은 `maskedText` + 숫자 `counts`뿐(위치·길이·조각 없음). 비속어 치환이 `'*'.repeat(word.length)` → 고정 `***`로 변경되어 길이 단서 제거(FR-3.5 권고 반영).
- API: `transcripts.service.ts:43` 이후 `rawText` 미참조, 저장·LLM·응답 모두 `maskedText`만. 신규 저장값은 `JSON.stringify(counts)`(숫자 5개)이고 이를 로깅하는 코드 없음(`apps/api/src` logger 3개소 모두 무관).
- 비밀정보: 이번 범위에 API 키 하드코딩·로그 노출 없음, `.env*` 변경 없음.
- 테스트 데이터(FR-5.3): 전부 합성(`test@example.com`, `4012888888888886` 표준 더미 등). `test.each('$input')`로 테스트 이름에 값이 노출되지만 합성 데이터라 위반 아님.

**결론: 원문의 저장/로그/전송 경로에는 신규 결함 없음. PII 관점 결함은 H-1(탐지 누락) 1건.**

## 7. NFR-3.1 (ReDoS) 점검

| 대상 | 정적 평가 | 실측 |
| ---- | --------- | ---- |
| `(?:[-.]\|\s+)?` 계열 전화/카드 5종 | 교차 없는 선택지, 반복 밖 고정 길이 — 안전 | 32KB 공백 패딩 0ms |
| `ACCOUNT_HYPHEN_PATTERN` | `\d{2,6}` 고정 상한, 중첩 수량자 없음 — 안전 | 102KB 8ms |
| `DIGIT_RUN_PATTERN` | 단일 수량자 — 안전 | 1MB 숫자열 11ms |
| `stripEdgePunctuation` | 앵커 고정 — 안전 | 1MB 한글 55ms |
| 이메일(변경 없음) | `+` + `\b` 시작 재시도 → **다항(2차)** | 102KB `12-12-…` 4,739ms |

**지수(catastrophic) 정규식은 없음.** 마지막 행이 M-1 근거이며, "정규식이 변경되지 않았으므로 안전"이라 판단할 수 없는 사례다(규칙 순서·치환 여부 변경이 다른 규칙의 입력 분포를 바꾼다). 트리거 조건은 클래스 런 안에 `\b`를 만드는 문자(`-.%+`)가 다수 포함된 긴 단일 토큰이며, 순수 영숫자 100KB 단일 토큰은 시작 위치가 1개라 225ms에 그친다.

## 8. 종합 의견

FR-1.1~1.3, FR-1.4, FR-2.1~2.3, FR-3 전체(옵션 B), FR-5(jest + 골든 코퍼스 84 tests), FR-6(데이터/로직 분리·근거 주석·하위 호환)이 요구사항대로 구현되었고, Phase 1에서 이관된 M-3/M-4의 **지적 케이스는 전부 해소**되었다. FR-1.5 2단계 구조 채택과 FR-4 구현의 스펙 일치도도 양호하다.

그러나 **AC-R-1은 무조건적 차단 기준**(DoD §10.2)이고 H-1이 정확히 이에 해당한다. 구분자가 일부만 있는 16자리 카드번호는 FR-2.2가 허용한 축소가 아니며, 마스킹 누락은 복구 불가능한 유출 방향이다. 따라서 H-1 수정 없이 Phase 3 완료로 판정할 수 없다. M-1은 NFR-3.2를 실측 위반하고 수정 비용이 매우 낮으므로(수량자 상한 2곳) H-1과 함께 처리 권고. M-2/M-3은 "과탐을 줄이러 들어간 Phase에서 새로 만든 과탐"이라 이번에 함께 정리하는 편이 합리적이다.
