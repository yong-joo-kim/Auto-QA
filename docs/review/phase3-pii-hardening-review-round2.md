## 4. 신규 발견 사항

### H-1(R2) (High, 차단) 공백 문자 클래스 축소 + 탭 누락으로 Phase 1 마스킹 케이스가 평문 잔존

- 위치: `packages/pii-mask/src/mask.ts:59`(`PHONE_CARD_SEP = '(?:[-.]|[ \\t]+)?'`), `:62`(`MANDATORY_SEP`), `:148`(`CARD_PARTIAL_SEP_PATTERN = /\b\d(?:\d|[-. ](?=\d))*\d\b/g`), `:158,160`(`/[-. ]/`)
- 원인: 1차 리뷰 §7이 기록한 것처럼 라운드 1 코드의 전화/카드 구분자는 `(?:[-.]|\s+)?`였다. M-2(개행 4줄 병합 과탐) 수정에서 `\s`를 `[ \t]`로 축소했는데, `\s`에 포함되던 **NBSP(U+00A0)·전각공백(U+3000)·얇은공백(U+2009)·VT·FF**까지 함께 떨어져 나갔다. 개행 제외만 필요했는데 같은-줄 공백까지 제외한 과잉 축소다. 신규 H-1 규칙은 별도로 `[-. ]`(탭 없음)을 쓰므로 탭도 누락된다.
- 실측(Phase 1 = 마스킹 / Phase 3 = 평문, 총 44조합):

| 규칙 | 손실 구분자 |
| ---- | ---------- |
| 휴대전화 `010␣1234␣5678` | NBSP, U+3000, U+2009, VT, FF, CR, LF |
| 유선전화 `02␣123␣4567`, `032␣1234␣5678` | NBSP, U+3000, U+2009, VT, FF, CR, LF |
| 카드 4-4-4-4 `4012␣8888␣8888␣8886` | NBSP, U+3000, U+2009, VT, FF, CR, LF |
| 카드 부분 구분자(H-1 신규 규칙) 4-4-8 / 8-8 | **TAB**, NBSP, U+3000, U+2009, VT, FF, CR, LF |

- 영향: 엑셀/CSV/워드/웹페이지에서 복사한 텍스트는 탭·NBSP·전각공백을 매우 흔히 포함한다. 예: `연락처 010　1234　5678`(전각공백)은 Phase 1에서 `[전화번호]`였으나 Phase 3에서 실제 번호가 그대로 `maskedText`로 DB 영구 저장 + LLM 전송된다. 원문 미저장 정책상 사후 재마스킹 불가 — 1차 H-1과 완전히 동일한 유출 유형이다.
- CR/LF 손실은 별건(M-2 트레이드오프)으로 §5에서 따로 다룬다.
- 권고(실측 검증 완료): 같은-줄 공백 클래스를 하나로 정의해 세 곳에 공통 적용한다.
  - `(?:[-.]|[^\S\r\n]+)` → 실측: SPACE/TAB/NBSP/U+3000/U+2009/VT/FF **전부 복구**, CR/LF는 계속 제외되어 M-2 개행 병합 과탐 **미재발**(`1234\n5678\n9012\n3456` 보존, `요금은 15000 20000 25000` 보존 확인)
  - 신규 규칙도 동일하게 `/\b\d(?:\d|[-.](?=\d)|[^\S\r\n](?=\d))*\d\b/g` 및 자릿수 산출용 strip 정규식을 맞춘다(현재 `replace(/[-. ]/g,'')`).
  - `PHASE1_REGRESSION_CASES`에 탭·NBSP·전각공백 케이스를 추가한다.

### M-1(R2) (Medium) H-1 신규 규칙이 "합계 16자리"만으로 인접 숫자를 병합해 날짜·소수 금액을 카드번호로 오탐

- 위치: `mask.ts:148`(`CARD_PARTIAL_SEP_PATTERN`), `:156-165`(`applyCardPartialSeparatorRule`)
- 원인: 패턴이 숫자·구분자를 한 토큰으로 최대한 길게 흡수한 뒤 **구분자 존재 + 합계 자릿수 16**만 검사한다. 그룹 개수·그룹 길이·날짜 형태를 보지 않으므로, 구분자로만 이어진 서로 다른 숫자들이 우연히 합계 16자리가 되면 통째로 치환된다.
- 실측(Phase 1은 전부 원문 보존):

| 입력 | Phase 3 결과 |
| ---- | ------------ |
| `가입일 2024-01-01 2025-12-31 입니다` | `가입일 [카드번호] 입니다` |
| `2026-09-11 2026-09-12 일정` | `[카드번호] 일정` |
| `기간 2024.01.01 2025.12.31` | `기간 [카드번호]` |
| `요금 1.234 5.678 9.012 3.456 원` | `요금 [카드번호] 원` |
| `수량 12 34 56 78 90 12 34 56 개` | `수량 [카드번호] 개` |
| `9001011234567 123` | `[카드번호]` (주민번호가 카드로 오귀속, counts 왜곡) |

- 영향: 유출 방향은 아니나(§1.1 허용 방향) AC-M이 고정한 **날짜 원문 보존(FR-2.3)** 취지를 인접 문맥에서 무너뜨리고, 계약기간·요금 나열은 통신/카드 상담 빈출 표현이라 "금액/기간을 정확히 안내했는가" 채점 근거가 사라진다. 1차 M-2가 지적한 "과탐을 줄이러 들어간 Phase에서 새 과탐 표면을 만드는" 패턴이 규칙만 바뀌어 재현되었다. 기존 코퍼스는 날짜를 단독(`오늘은 2026-09-11 입니다`) 또는 `~` 삽입(`2024-01-01 ~ 2025-12-31`)으로만 담고 있어 이 결함을 잡지 못한다.
- 권고: 신규 규칙에 구조 제약 추가 — ① 구분자로 나뉜 **그룹 수 ≤ 4**, ② 각 그룹 **2자리 이상**, ③ 토큰 내부에 `(19|20)\d{2}[-.]\d{2}[-.]\d{2}` 날짜 형태가 포함되면 제외. 실측 확인: H-1 4케이스는 모두 2~3그룹(각 4자리 이상)이라 유지되고, 위 6케이스는 6~8그룹 또는 1자리 그룹으로 전부 배제된다. 6케이스를 `FALSE_POSITIVE_CASES`에 추가한다.

### L (신규)

- **L-1(R2)** 이메일 `{1,64}` 상한의 부작용: 로컬파트 65자 이상이면 `\b` 시작점이 없어 **전혀 매칭되지 않는다**(실측: 65/80자 → 평문 전체 잔존, 로컬파트에 `.`/`-`가 있으면 앞부분만 평문으로 남고 뒤만 `[이메일]`로 부분 마스킹). Phase 1은 마스킹했다. RFC 5321 로컬파트 상한이 64라 정상 주소는 영향 없어 Low이나, STT 오인식/붙여쓰기로 긴 토큰이 생기면 유출 방향이다. 상한 유지 시 주석에 "65자 이상은 의도적 미탐"을 명시하거나, `\b` 대신 `(?<![A-Za-z0-9._%+-])` 경계 + 상한 완화를 검토.
- **L-2(R2)** 종류 오귀속 사례 증가(1차 L-5 연장): `9001011234567 123` → `[카드번호]`. FR-4 요약 건수가 실제 종류와 달라진다(유출 아님).
- **L-3(R2)** 요구사항 문서 미기록 편차 2건: ① M-2 수정으로 CR/LF 구분자 전화/카드 케이스가 Phase 1 대비 미마스킹으로 전환(개행 병합 과탐 제거의 대가, 1차 리뷰 권고에 근거), ② M-3 날짜 가드로 `계좌 20260911`처럼 **YYYYMMDD 형태의 실제 8자리 계좌**는 문맥 키워드가 있어도 미마스킹(연도 1900~2099 대역에 한정). 둘 다 타당한 트레이드오프이나 AC-R-1이 차단 기준이므로 AC-L-3의 "구현 편차 기록(2026-09-12)"과 동일한 방식으로 **요구사항 §7에 승인 편차로 기록**해야 추적 가능하다. 현재는 코드 주석·코퍼스 note에만 있다.
- **L-4(R2)** 1차 L-6(잔존 미탐 문서화 권고) 미이행 — `+82-2-1234-5678`, `02)123-4567`, 17자리 무구분 계좌, Luhn 탈락 무구분 16자리. 헤더 주석 또는 코퍼스 "알려진 한계" 절에 고정 권고.

## 8. 종합 의견

1차 지적 11항목 중 **9항목이 실측으로 해소**되었고(H-1 보고 케이스, M-1~M-4, L-1~L-4), 특히 M-1은 4,811ms → 27ms로 NFR-3.2를 충분한 마진으로 만족하고 M-4는 오탐 회귀 없이 미탐만 회복했다. FR-4 구현과 UI 스펙 §5.3/§5.4 부합도 완결되었다. 수정 품질 자체는 방향과 근거 주석 모두 양호하다.

그러나 **AC-R-1은 무조건적 차단 기준**(DoD §10.2, NFR-1.1)이고, H-1(R2)가 정확히 이에 해당한다. 1차 H-1이 "구분자 있음"을 너무 좁게 해석한 결함이었다면, 이번은 "공백"을 너무 좁게 해석한 결함으로 **손실 유형이 동일**하다(Phase 1 마스킹 → Phase 3 평문 저장·전송, 복구 불가). 44조합 중 탭·NBSP·전각공백은 실제 상담 데이터에서 충분히 발생 가능하므로 수용할 수 없다. 수정 비용은 낮다 — 같은-줄 공백 클래스 `[^\S\r\n]`를 3개소에 공통 적용하면 되고, M-2 과탐 미재발까지 본 리뷰에서 실측 검증했다.

M-1(R2)는 유출 방향이 아니어서 차단은 아니지만, H-1 수정이 직접 만든 부작용이고 AC-M의 날짜 보존 취지를 침식하므로 같은 라운드에서 함께 정리하는 것이 합리적이다(구조 제약 3개, 코퍼스 6케이스).

**최종 판정: H-1 / AC-R-1 미통과 → Phase 3 완료 불가. backend-implementer 재작업 1회 필요.** 재작업 범위는 `mask.ts` 3개소 + 코퍼스로 국한되며, 비속어(FR-3)·FR-4·프런트엔드는 추가 작업 없음(이번 라운드 통과). H-1(R2)/M-1(R2) 수정 후에는 본 리뷰의 구분자 전수 조합 차분과 날짜·금액 인접 케이스만 재확인하면 되므로 3차 리뷰는 경량으로 가능하다.
