# Phase 1 — Vertical Slice (통신 도메인, Mock LLM) UI 설계서

- 관련 문서: `docs/requirements/phase1-vertical-slice.md`, `docs/architecture/eval-sheet-schema.md`, `seed/eval-sheets/03-telecom.json`
- 산출물 소비자: `frontend-implementer`
- 범위: 트랜스크립트 입력 → 제출 → 로딩 → 결과 표시(카테고리 소계/항목별 상세/게이팅/등급/총점). 통신(telecom) 도메인 1건 고정. 이력 목록, 다중 도메인 선택, 평가시트 관리 화면은 이번 Phase 범위 밖(요구사항 §7 Out of scope).
- 코드(React 컴포넌트 등)는 포함하지 않음. 컴포넌트 분해·props·상태·인터랙션만 정의한다.

## 1. 화면 목록 및 라우트

| # | 라우트 | 화면명 | 목적 | 진입 경로 |
|---|---|---|---|---|
| 1 | `/transcripts/new` | 트랜스크립트 입력 화면 | 상담대화 원문 입력, 도메인(telecom 고정) 확인, 제출 및 제출 중 상태 표시 | 앱 진입 시 기본 화면(루트 `/` → `/transcripts/new` 리다이렉트 권장). 결과 화면에서 "새 평가" 버튼으로도 재진입 |
| 2 | `/transcripts/:id` | 평가 결과 상세 화면 | 카테고리별 소계 → 항목별 상세(배점/획득점수/사유) → 게이팅 결과 → 총점/등급 표시 | (a) 입력 화면에서 제출 성공 시 자동 이동 (b) 저장된 ID로 URL 직접 접근(새로고침/북마크/공유) 시 재조회 |

Phase 1은 이 두 화면만 존재한다. 헤더/네비게이션에 "이력 목록", "평가시트 관리" 등의 링크를 노출하지 않는다(향후 Phase에서 추가될 자리로 헤더 우측에 "Phase 2 예정" 같은 자리표시자를 두는 것은 선택 사항이며 필수는 아니다).

## 2. 화면별 목적 / 상태별 UI

### 2.1 `/transcripts/new` — 트랜스크립트 입력 화면

**목적**: QA 관리자가 상담대화 원문을 붙여넣고, 도메인(통신 고정)을 확인한 뒤 제출하여 채점을 요청한다.

**상태 정의**

| 상태 | 트리거 | 화면 표현 |
|---|---|---|
| `idle` (기본) | 최초 진입 | 빈 입력 폼, 제출 버튼 활성(입력 전에는 클릭 시 클라이언트 검증만 수행) |
| `invalid` | 제출 클릭 시 rawText가 비어있거나 공백 제외 10자 미만 | textarea 하단에 인라인 에러 메시지, textarea에 `aria-invalid="true"`, 포커스를 textarea로 이동. 서버 호출 없음(FR-1.2, AC-2) |
| `submitting` | 클라이언트 검증 통과 후 `POST /transcripts` 요청 전송 중 | 제출 버튼 비활성 + 로딩 스피너로 전환, textarea/도메인선택 비활성화(재제출 방지), 폼 영역 상단 또는 버튼 옆에 "채점 진행 중입니다..." 텍스트 인디케이터 표시(FR-7.4) |
| `submit-error` | 서버 오류(500/504, 계약 위반 502 등) 또는 네트워크 실패 | 폼 위에 오류 배너(비-색상 단서 포함: 경고 아이콘 + "채점 요청이 실패했습니다" 텍스트) + "다시 시도" 버튼. 입력 내용은 保존되어 재수정 없이 재시도 가능(NFR-3.2, AC-5, FR-7.5) |
| `redirecting` | 서버 응답 성공(트랜스크립트/평가 저장 완료, id 수신) | 짧게 성공 상태 표시 후 `/transcripts/:id`로 라우팅 |

**정보 구조(위→아래)**: 화면 설명 → 도메인 선택 → 트랜스크립트 textarea(+글자수/최소길이 안내) → 선택 메타데이터(접기 가능) → PII 마스킹 고지 → 오류 배너(있을 때만) → 제출 버튼.

### 2.2 `/transcripts/:id` — 평가 결과 상세 화면

**목적**: 저장된 평가 결과를 카테고리 소계 → 항목별 상세 → 게이팅 → 총점/등급 순으로 한눈에 검토할 수 있게 표시한다.

**상태 정의**

| 상태 | 트리거 | 화면 표현 |
|---|---|---|
| `loading` | `GET /transcripts/:id` (또는 `GET /evaluations/:id`) 요청 중 — 입력 화면에서 막 넘어온 직후, 또는 URL 직접 접근 시 | 스켈레톤 또는 중앙 스피너 + "평가 결과를 불러오는 중입니다" 텍스트 |
| `success` | 응답 200 정상 수신 | §3의 전체 결과 레이아웃 렌더링 |
| `not-found` | 404 (존재하지 않는 id, NFR-3.4) | "요청하신 평가 결과를 찾을 수 없습니다" 안내 + "새 평가 시작하기" 버튼(→ `/transcripts/new`) |
| `error` | 5xx/네트워크 오류 | "결과를 불러오지 못했습니다" 안내 + "다시 시도" 버튼(재조회) |

이 화면에는 별도의 "빈 상태"가 없다(ID가 있으면 반드시 결과가 존재하거나 404).

## 3. 컴포넌트 분해 및 데이터 바인딩

### 3.1 `/transcripts/new` 컴포넌트 트리

```
TranscriptNewPage (컨테이너)
├── PageHeader            — 제목("상담대화 평가 요청"), 설명 1~2줄
├── DomainSelector
│     props: { domains: DomainOption[], value: "telecom", disabled: false, onChange }
│     - DomainOption = { domainId, domainName, enabled: boolean, disabledReason?: string }
│     - Phase 1: seed 10개 도메인 목록을 옵션으로 노출하되 telecom만 enabled=true,
│       나머지는 disabled=true + disabledReason="Phase 2 예정"(select 옵션 비활성 또는
│       라디오 그룹에서 비활성 스타일 + 텍스트 뱃지로 표기)
│     - value는 telecom으로 고정, 사용자가 변경 불가(읽기전용 표시로도 대체 가능)
├── TranscriptTextarea
│     props: { value, onChange, minLength: 10 (공백 제외 기준),
│               errorMessage?: string, disabled: boolean(submitting 시 true) }
│     - 하단에 실시간 글자수 카운터("공백 제외 N자 / 최소 10자") 표시
│     - errorMessage 존재 시 textarea 테두리 강조 + 텍스트 메시지 동시 표시(색상 단독 금지)
├── MetadataFieldsAccordion (선택, 기본 접힘)
│     props: { agentId?, consultedAt?, channel?: "voice"|"chat", onChange }
│     - FR-1의 선택 필드. 채점 로직에 영향 없음을 라벨 옆 보조텍스트로 안내
├── PiiNoticeCallout
│     - 정적 안내: "전화번호·이메일·주민등록번호·카드번호 등은 자동 마스킹 후 저장/전송됩니다.
│       단, 정규식 기반 탐지로 100% 탐지를 보장하지 않습니다." (NFR-1.3 고지, 필수 아님이나 채택)
├── SubmissionErrorBanner (submit-error 상태일 때만 렌더)
│     props: { message: string, onRetry: () => void }
├── SubmitBar
│     ├── SubmitButton   props: { label: "채점 요청", loading: boolean, disabled: boolean }
│     └── LoadingIndicator (submitting일 때만) — 스피너 + "채점 진행 중입니다 (수 초 소요될 수 있습니다)"
```

**클라이언트 → 서버 데이터 바인딩** (요구사항 §4.1 그대로)

```jsonc
POST /transcripts
{
  "domainId": "telecom",
  "rawText": "<textarea 값>",
  "metadata": { "agentId"?, "consultedAt"?, "channel"? }  // 값이 없으면 필드 생략 또는 null
}
```

- 성공 응답에 `transcriptId`(또는 `evaluationId`) 포함 → `navigate(/transcripts/${id})`.
- 프론트는 `totalScore`, `grade`, `gatingResult` 등 결과값을 절대 직접 계산하지 않는다(NFR-5.1). 입력 화면은 오직 rawText/domainId/metadata만 서버로 보낸다.

### 3.2 `/transcripts/:id` 컴포넌트 트리

정보 구조 원칙(요구사항 §3, 아키텍처 §6): **게이팅 결과(눈에 띄게, 총점과 분리) → 총점/등급 → 카테고리별 소계 → 항목별 상세(배점/획득점수/사유) → 부가정보(출처/디스클레이머/메타)** 순으로 배치한다. 게이팅은 총점보다 시각적으로 먼저/위에 오도록 하여 "총점이 높아도 탈락일 수 있다"는 오해를 방지한다(아키텍처 §변경사항 5).

```
TranscriptResultPage (컨테이너, :id로 GET 요청)
├── ResultPageHeader
│     props: { domainName: "통신(이동통신·인터넷)", createdAt, transcriptId }
│     - 우측에 "새 평가 시작하기" 링크(→ /transcripts/new)
│
├── GatingBanner                       ★ 최상단, 가장 눈에 띄는 요소
│     props: { gatingResult: "통과" | "탈락(재검토 필요)",
│               failedGatingItems?: { itemId, itemName, reason }[] }
│     - "탈락": 경고 아이콘 + 굵은 텍스트 "탈락(재검토 필요)" + 실패한 게이팅 항목명 나열
│       (배경색만이 아니라 아이콘·굵은 라벨 텍스트로 상태 전달, §5 접근성 참조)
│     - "통과": 체크 아이콘 + "통과" 텍스트(강조는 하되 탈락 배너보다 시각적 무게는 낮게)
│     - 안내 문구 고정 노출: "게이팅 탈락 시 총점·등급과 무관하게 재검토가 필요합니다."
│
├── TotalScoreSummary
│     props: { totalScore: number, totalMaxScore: 100, grade: "우수"|"양호"|"보통"|"미흡" }
│     - "총점 87 / 100", "등급: 양호" 형태. 등급 옆에 게이팅 탈락 시
│       "(게이팅 탈락으로 재검토 필요 — 등급은 참고용)" 보조텍스트 병기(FR-5.4)
│
├── CategoryScoreOverview                — 카테고리 소계 5건, 표/카드 그리드
│     props: { categories: { categoryId, categoryName, score, maxScore }[] }
│     └── CategoryScoreCard × 5
│           props: { categoryName, score, maxScore }
│           - "기본응대 12/15", "컴플라이언스 22/30" 등. 클릭 시 아래 상세 섹션으로 스크롤/포커스 이동
│
├── ItemDetailSections                   — 카테고리별 항목 상세, 카테고리 순서 고정
│     (basic-response → attitude → expertise → efficiency → compliance)
│     └── ItemDetailSection × 5 (카테고리 1개당 1섹션)
│           props: { categoryId, categoryName, categoryScore, categoryMaxScore, items }
│           └── ItemDetailRow × N (섹션 내 항목 수만큼, 13건 합계)
│                 props: {
│                   itemId, itemName, criteria?,
│                   score: number, maxScore: number,
│                   reason: string,
│                   gating: boolean,
│                   passFail?: "P" | "F"     // gating=true인 항목만 존재
│                 }
│                 - 배점/획득점수는 "4 / 5"처럼 병기(획득만 보이지 않게)
│                 - gating=true 항목은 행 좌측에 "게이팅" 텍스트 라벨 + P/F 배지를
│                   함께 표시(텍스트 라벨 필수, 색상만으로 P/F 구분 금지)
│                 - reason은 전체 문장 표시(말줄임 금지, 필요 시 펼치기/접기 아님 — 사유가
│                   짧은 템플릿 문장이므로 기본 전체 노출)
│
├── ComplianceFootnote (선택, compliance 섹션 하단에 위치)
│     props: { sourceCitation: string, disclaimer: string }
│     - 작은 글씨로 출처/면책 문구 표시(아키텍처 §변경사항 6, 선택 사항)
│
└── EvaluationMetaFooter (선택, 화면 최하단)
      props: { evalSheetVersion, llmProvider, llmModel, createdAt }
      - QA 관리자가 어떤 평가시트 버전·프로바이더로 채점되었는지 확인 가능(FR-6.2 저장값 노출)
```

**서버 → 클라이언트 데이터 바인딩** (요구사항 §4.4 저장 스키마를 그대로 조회 응답으로 사용한다고 가정)

```jsonc
GET /transcripts/:id  또는  GET /evaluations/:id
{
  "id": "uuid",
  "domainId": "telecom",
  "domainName": "통신(이동통신·인터넷)",
  "evalSheetVersion": "1.0.0",
  "llmProvider": "mock",
  "llmModel": "mock-v1",
  "items": [ { "itemId", "categoryId", "itemName"?, "score", "maxScore", "reason", "passFail" } ],
  "categoryScores": [ { "categoryId", "categoryName"?, "score", "maxScore" } ],
  "totalScore": 0,
  "totalMaxScore": 100,
  "grade": "우수|양호|보통|미흡",
  "gatingResult": "통과|탈락(재검토 필요)",
  "sourceCitation": "string?",
  "disclaimer": "string?",
  "createdAt": "ISO8601"
}
```

- `itemName`/`categoryName`이 저장 스키마(§4.4)에는 없으므로, 백엔드 응답에 표시용 이름을 포함하거나 프론트가 평가시트 정적 데이터(telecom 시트)를 참조해 `itemId`/`categoryId`로 이름을 매핑해야 한다. 이 매핑 방식(응답 포함 vs 프론트 참조)은 `backend-implementer`/`frontend-implementer` 협의 사항으로, 본 설계서는 화면에 **이름이 반드시 표시되어야 함**만 규정한다.

## 4. 사용자 인터랙션 흐름

### 4.1 정상 흐름 (AC-1)

```
[idle] 입력 화면 진입
   │  도메인=telecom(고정), 트랜스크립트 입력
   ▼
사용자가 "채점 요청" 클릭
   │
   ├─ 클라이언트 검증 실패(공백 제외 10자 미만) ─▶ [invalid] 인라인 에러 표시, 여기서 종료(서버 호출 없음)
   │
   ▼ (검증 통과)
[submitting] 폼 비활성화 + 로딩 인디케이터, POST /transcripts 전송
   │
   ├─ 실패(4xx/5xx/네트워크) ─▶ [submit-error] 오류 배너 + "다시 시도" 버튼
   │        │
   │        └─ "다시 시도" 클릭 ─▶ [submitting]으로 재진입 (입력값 유지)
   │
   ▼ 성공(200/201, id 수신)
[redirecting] → navigate(/transcripts/:id)
   │
   ▼
[loading] 결과 화면에서 GET 요청(또는 제출 응답을 그대로 사용해 즉시 렌더 — 구현 선택)
   │
   ├─ 실패 ─▶ [error] "다시 시도" 버튼 → GET 재요청
   │
   ▼ 성공
[success] 게이팅 배너 → 총점/등급 → 카테고리 소계 → 항목별 상세 렌더
```

### 4.2 게이팅 탈락 흐름 (AC-3)

- `[success]` 상태 진입 시 `gatingResult === "탈락(재검토 필요)"`이면 `GatingBanner`가 경고 스타일(아이콘+굵은 텍스트)로 최상단에 즉시 표시되고, 페이지 진입 시 포커스를 배너로 이동시켜 스크린리더 사용자도 즉시 인지하도록 한다(`role="alert"` 또는 `aria-live="assertive"` 권장).
- `TotalScoreSummary`의 등급 표기 옆에도 "게이팅 탈락으로 재검토 필요" 보조 텍스트를 병기하여, 사용자가 카테고리/항목 상세만 보고 총점만으로 오판하지 않게 한다.

### 4.3 LLM(Mock) 오류 흐름 (AC-5)

- `MOCK_LLM_FAILURE_RATE > 0`으로 서버가 오류를 반환하면 입력 화면은 `[submit-error]`에 머무른다(결과 화면으로 이동하지 않음 — 저장되지 않은 레코드를 조회할 수 없으므로 애초에 id가 없다).
- 오류 배너 문구 예: "채점 요청 처리 중 오류가 발생했습니다. 잠시 후 다시 시도해 주세요." + "다시 시도" 버튼.
- 재시도 시 동일 입력값으로 재제출(사용자가 다시 타이핑할 필요 없음).

### 4.4 URL 직접 접근 / 새로고침 (FR-6.3, NFR-3.4)

```
사용자가 /transcripts/:id URL로 직접 진입 또는 새로고침
   ▼
[loading] GET 요청
   ├─ 200 ─▶ [success]
   ├─ 404 ─▶ [not-found] "결과를 찾을 수 없습니다" + "새 평가 시작하기"
   └─ 5xx/네트워크 실패 ─▶ [error] "다시 시도" 버튼
```

### 4.5 빈 입력 검증 (AC-2)

```
textarea 비어있음(또는 공백 제외 10자 미만) 상태에서 "채점 요청" 클릭
   ▼
[invalid] textarea 인라인 에러 메시지 표시, aria-invalid=true, 포커스 이동
   ※ 서버 호출 발생하지 않음. 결과 화면으로 이동하지 않음.
```

## 6. 접근성 / 반응형 고려사항

**접근성**

1. **색만으로 상태 구분 금지**: 게이팅 통과/탈락, P/F 배지, 점수 구간(고/저)은 색상뿐 아니라 아이콘 + 텍스트 라벨(예: "통과"/"탈락(재검토 필요)", "P"/"F" 텍스트)을 항상 함께 표시한다. 저채도/흑백 환경에서도 정보가 전달되어야 한다.
2. **긴급 정보 알림**: 게이팅 탈락 배너는 `role="alert"` 또는 `aria-live="assertive"`로 스크린리더에 즉시 낭독되게 한다. 일반 로딩/성공 전환은 `aria-live="polite"` 수준으로 충분하다.
3. **폼 접근성**: textarea에 명시적 `<label>` 연결, 에러 시 `aria-invalid="true"` + `aria-describedby`로 에러 메시지 연결. 필수 입력 표시(`*`)는 텍스트로도 "(필수)"를 함께 제공.
4. **포커스 관리**: 제출 실패 시 포커스를 오류 배너 또는 재시도 버튼으로 이동. 결과 화면 진입 시(게이팅 탈락인 경우) 포커스를 `GatingBanner`로 이동. 페이지 전환(입력→결과) 시 포커스를 페이지 제목(`h1`)으로 이동.
5. **키보드 접근성**: 도메인 선택(비활성 옵션 포함), 카테고리 아코디언 펼치기/접기, 재시도 버튼 모두 키보드만으로 조작 가능해야 하며, 비활성 도메인 옵션은 `disabled` 속성과 `aria-disabled`를 함께 사용하고 이유(`disabledReason`)를 `title`/보조텍스트로 노출.
6. **명도 대비**: 경고(탈락)·정상(통과) 배지 모두 WCAG AA 대비 기준(텍스트 4.5:1) 충족. 강조색은 텍스트/아이콘과 함께 사용하되 배경색 단독 의존 금지.
7. **표 vs 카드 선택**: `ItemDetailRow`를 실제 `<table>`로 구현할 경우 `<th scope="col">`로 "항목명/배점/획득점수/사유/게이팅" 열을 명시하고, 카드 레이아웃으로 구현할 경우 각 필드에 시각적 라벨(작은 캡션)을 반드시 병기하여 스크린리더가 "라벨: 값" 구조로 읽히게 한다.

**반응형 레이아웃**

- 브레이크포인트 기준(예): 모바일 `< 640px`, 태블릿 `640–1024px`, 데스크톱 `> 1024px`.
- **입력 화면**: 모바일에서 도메인 옵션 목록은 세로 스택 + 접기(기본은 telecom만 보이고 "다른 도메인 보기" 토글로 나머지 9개 노출)로 화면 스크롤 최소화. textarea는 모든 breakpoint에서 최소 높이(예: 200px) 확보, 세로로 자유롭게 늘어나도록 함.
- **결과 화면**: `CategoryScoreOverview`는 데스크톱에서 5열 그리드, 태블릿 2~3열, 모바일 1열 스택으로 전환. `ItemDetailSection`(카테고리별 아코디언)은 모든 breakpoint에서 기본 구조 동일(세로 스택)하되, 모바일에서는 항목명/배점/사유를 세로로 쌓아 가로 스크롤이 생기지 않게 한다(표 형태 대신 카드형 권장).
- `GatingBanner`, `TotalScoreSummary`는 항상 화면 상단 고정 영역에 위치하며, 긴 스크롤 후에도 재확인이 쉽도록 모바일에서는 상단 sticky 처리를 고려할 수 있다(선택 사항).

## 7. 구현 시 유의사항 요약 (frontend-implementer용)

- 결과 화면의 정보 노출 순서는 **게이팅 → 총점/등급 → 카테고리 소계 → 항목 상세**를 반드시 지킨다(요구사항 §3, 아키텍처 §변경사항 5의 명시적 요구).
- 프론트는 `totalScore`/`grade`/`gatingResult`/`categoryScores`를 절대 재계산하지 않고 서버 응답값을 그대로 표시한다(NFR-5.1).
- 도메인 선택 UI는 반드시 10개 도메인을 노출하되 telecom 외 비활성 처리한다(FR-1.3). telecom만 렌더링하고 나머지를 아예 숨기는 것은 요구사항 위반이다.
- 로딩 인디케이터는 Mock 기준으로도 수 초가 걸릴 수 있음을 전제로 반드시 구현한다(NFR-4.1) — 즉시 응답을 가정한 UI(스피너 생략)는 허용되지 않는다.
- 오류 메시지는 원문/마스킹 텍스트 내용을 노출하지 않는다(로그/화면 모두 NFR-1.2 원칙 준수).
